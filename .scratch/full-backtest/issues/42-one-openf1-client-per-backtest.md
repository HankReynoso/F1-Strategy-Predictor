# 42: Use one OpenF1 client for a whole Backtest

**What to build:** The router builds a new OpenF1 client for every race, so the client's 3-per-second / 30-per-minute tracking resets between races. On a cold cache, requests from consecutive races can burst past OpenF1's limit, causing 429 back-offs or "fetch failed" Excluded Races. Build one client per Backtest (and per Smoke Set or single-race run) and pass it through.

**Decisions and alternatives rejected.**

- *Build the client in the CLI and pass it down.* The CLI already creates the loader for each command and is the one place that knows what "a run" is.
  - Rejected: a module-level shared client inside `data` (one per process). It would make two runs in one process (the tests, a notebook) share rate-limit memory and a cache directory chosen at import time, which is the "one per process" case the third test rules out.
  - Rejected: a client parameter on `run_backtest`. The Backtest takes a loader and knows nothing about sources (ADR-0006's seam). Adding OpenF1 to it would leak the source choice upwards.
- *Leave `data.load_weekend`'s own default (a new client when none is passed).* Direct callers (the notebook, single-race scripts, fast tests) still work. Every top-level command now passes one.
- *Bind the client with `functools.partial`* rather than a closure: it keeps the loader's signature visible and adds no new function.

**Deviations from the ticket / spec.** None. No spec, `CONTEXT.md` or ADR change: this is wiring, and ADR-0006's seam is unchanged.

**Open questions, known limitations and follow-ups.**

- *FastF1's offline mode doesn't survive the loaders.* `fastf1.Cache.offline_mode(True)` sets a flag on the current HTTP session. `fastf1_loader` calls `fastf1.Cache.enable_cache` on every load, which builds a new session and silently turns offline mode off. The comparison above kept it on by enabling the cache once and making later `enable_cache` calls no-ops in the run script. Consequences:
  - Ticket 38's notes, and ticket 37's, say their runs were FastF1-offline; they were not. For ticket 38 the effect is only that a stale schedule could have been re-fetched; the numbers stand. Ticket 38 now carries a correction.
  - Rebuilding the session on every load is also wasted work, noted on ticket 44.
- *Offline-mode misses look like refusals.* A request that offline mode refuses is reported by FastF1 the same way as an archive refusal, so Spain 2022's warnings read identically offline and online. Harmless for a comparison; worth knowing before reading an offline run's warnings as evidence about the archive.
- The slow Smoke Set test wasn't re-run online after its one-line change, to spare FastF1's hourly budget. The CLI comparison above covers the same races through the same code, and the test still collects (4 tests).

**Review feedback to the user.** The change is ten lines in `cli.py`. The bug only shows on a cold cache, where the old code could start each race with a burst that the previous race had already used up, causing 429 back-offs or "fetch failed" exclusions. Ticket 24's full re-run is the first cold run that benefits.
