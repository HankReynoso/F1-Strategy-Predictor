# 21: OpenF1 pre-race weekend loader

**What to build:** `src/f1_strategy/openf1_loader.load_weekend` that builds `PreRaceInfo` + the `Session`/`Lap` tuples for every pre-race session (FP1–FP3 or FP1+Sprint+SQ, plus Q) for a 2023+ race weekend. Mirrors the shape of `fastf1_loader.load_weekend` so the two sit behind one seam. Derivations required (recipes verified against real responses in the findings):
- Round number from meeting date order.
- Sprint vs conventional from the session set.
- Driver TLA from `/v1/drivers.name_acronym`.
- Compound/tyre_age/new_when_fitted per lap from `/v1/stints` joined onto `/v1/laps`.
- `pit_in` per lap from `/v1/pit.lap_number`; `pit_out` from `/v1/laps.is_pit_out_lap`.

**Blocked by:** 20 (client).

**Status:** done

**Category:** enhancement

Field-by-field recipes and sample responses in [`openf1-findings.md`](../openf1-findings.md). Follow-up from [ticket 18](18-check-openf1-as-second-data-source.md).

**Out of scope:** the race session, pit loss and historical degradation — ticket 22.

## Implementation notes

**What was built (2026-10-23), test-first.**

- `src/f1_strategy/openf1_loader.py` — new module, ~330 lines. One public call `load_weekend(season, event, *, client=None, cache_dir=".cache/openf1") -> RaceWeekend` that mirrors `fastf1_loader.load_weekend`'s signature and return shape. Internally it drives the ticket-20 client through a narrow `_OpenF1Client` protocol (one method, `get(endpoint, **params) -> list[dict]`) so fixture tests inject a fake without a cache dir or network stack.
  - `_find_meeting` resolves `event` against `meeting_name`, `location` or `country_name` case-insensitively; the first match wins. Testing weekends are filtered out by `_is_race_meeting`, which keys off the "Grand Prix" suffix in `meeting_name` — the one derivation the findings table lists ("Pre-Season Testing" is the only non-round entry).
  - `_round_number` is a module-private helper (not called by `load_weekend` itself, since `PreRaceInfo` carries no round field) that gives 1-indexed round numbers from the yearly meetings list sorted by `date_start`. Exposed so ticket 23's `list_season` can read it without re-deriving the rule.
  - `_is_sprint_weekend` tests "Sprint" ∈ session names. This catches both the 2023 session set (which included "Sprint Shootout") and the 2024+ set (which has "Sprint Qualifying") because the sprint **race** itself kept the name "Sprint" through F1's rename of its qualifier.
  - `_ordered_pre_race_sessions` filters OpenF1's session rows through `_SESSION_SHORT_NAME` and reorders them on the canonical `("FP1", "FP2", "FP3", "SQ", "S", "Q")` sequence — the order the predictor reads. The race session is always excluded.
  - `_teams` reads `/v1/drivers?session_key=<race>` for the number→(TLA, team) mapping and `/v1/starting_grid?session_key=<quali>` for the race's starter set. OpenF1 attaches the main race's starting grid to the **qualifying** session, not the race, which the findings table flags explicitly.
  - `_load_pre_race_session` fetches `/v1/laps`, `/v1/stints` and `/v1/pit` for the session, indexes stints per driver sorted by `lap_start`, and builds a per-driver `set` of pit-in lap numbers. `_laps_from` then yields one `Lap` per usable row, matching lap→stint by closed-interval range (`lap_start ≤ lap_number ≤ lap_end`).
  - Per-lap derivations exactly as the findings describe: `lap_time = lap_duration`, `tyre_age = (lap_number - stint.lap_start) + 1 + stint.tyre_age_at_start`, `new_when_fitted = (stint.tyre_age_at_start == 0)`, `pit_in = lap_number ∈ pit_rows[driver]`, `pit_out = row.is_pit_out_lap`. `tyre_set` follows the FastF1 loader's `"{driver}-{session}-stint{N}-{compound}"` pattern so a cross-source history (ticket 23 + ticket 11) counts stints the same way whichever loader built them.
  - `_race_laps_count` reads `/v1/session_result?session_key=<race>` and returns the max `number_of_laps` across the result set (equivalent to the winner's lap count — DNFs have fewer). `race_laps` is a `PreRaceInfo` field so it has to be populated now even though ticket 22 owns the race side; this one call is the cheapest derivation the findings offer.
- `tests/fixtures/openf1/monza_2024.json` and `austria_2024.json` — recorded responses, trimmed to two drivers (VER/LEC at Monza; VER/NOR at Austria) and the minimum lap/stint/pit rows the assertions exercise. Each fixture is a JSON object mapping request URL suffix (e.g. `"laps?session_key=9581"`) to the response list. The `_about` key documents what the fixture covers. Austria includes a sprint stint with `tyre_age_at_start=5` so the used-set path is exercised exactly as the findings sampled it.
- `tests/test_openf1_weekend_loader.py` — 32 fast tests (~0.5 s). `_FixtureClient` reconstructs the URL key from an endpoint and sorted kwargs and raises when a fixture row is missing, so a missing recording surfaces as a test failure rather than a silent `[]`. Coverage:
  - **Shape & matching**: returns a `RaceWeekend`; circuit comes from `meeting.location`; `event` matches on name/location/country case-insensitively; unknown events raise; testing weekends never match.
  - **Format detection**: Monza is conventional, Austria is sprint; `_is_sprint_weekend` catches both session sets.
  - **Session set**: FP1/FP2/FP3/Q for conventional; FP1/SQ/S/Q for sprint; race session is never in `pre_race.sessions`; `race` is an empty `RaceOutcome` and `pit_loss` is 0.0 (ticket 22 scope).
  - **Teams**: Monza grid resolves to {VER→Red Bull, LEC→Ferrari}; Austria sprint-weekend grid uses the **main** `Qualifying` session, not Sprint Qualifying.
  - **Per-lap derivations**: every lap carries the required fields; `lap_time` is the raw `lap_duration` in seconds; `compound` comes from the covering stint; laps with `lap_duration=null` are skipped; laps outside every stint range are skipped (recorded ambiguity decision); `tyre_age` starts at 1 for a new stint's first lap and at `1 + tyre_age_at_start` for a used stint; `new_when_fitted` is True for `tyre_age_at_start==0` and False otherwise; `pit_in` reflects the `/v1/pit` lap numbers; `pit_out` reflects `is_pit_out_lap`; `tyre_set` follows the FastF1 pattern byte for byte.
  - **Neutralised flag**: False for every pre-race lap (recorded ambiguity decision — see below).
  - **race_laps**: Monza = 53 (winner's number_of_laps); Austria = 71 (max across the result, since the fixture also includes a DNF row at 64 laps to pin that we take the max, not the first row).
  - **Round number helper**: 1-indexed order from `date_start`, testing row excluded.
- `tests/test_openf1_weekend_loader_real_data.py` — one `@pytest.mark.slow` module with 5 tests that load Monza 2024 through the real `OpenF1Client` (its on-disk cache under `.cache/openf1`, already gitignored). Runs in ~10 s cold, ~0.1 s warm.

**Decisions and alternatives rejected.**

- *`pit_loss = 0.0` placeholder for ticket 22 to replace.* The alternative was to make `pit_loss` optional on `PreRaceInfo` or compute it here as a bare passthrough. Rejected both — changing the dataclass is scope creep for ticket 22, and computing Pit Loss now would duplicate the work ticket 22 is explicitly chartered for. A test pins the placeholder so a reader doesn't mistake the zero for a real Pit Loss, and the loader docstring says ticket 22 fills it in.
- *Fetch `/v1/drivers` once from the race session, not once per pre-race session.* OpenF1's number→TLA mapping is weekend-stable (the TLA for a driver number doesn't change between FP1 and the race). One fetch instead of four halves the loader's request budget per weekend (10 → 7 for a conventional weekend, 12 → 9 for a sprint weekend), which matters against the 30-req/min free-tier cap, and keeps the fixtures smaller. The alternative — one drivers fetch per session — was what my first draft wrote; the fixture miss ("no drivers?session_key=9581") in the first test run pushed me to re-examine it, and the fetch is genuinely redundant.
- *A narrow `_OpenF1Client` protocol instead of hard-typing on `OpenF1Client`.* Lets tests pass a `_FixtureClient` with no network, no cache, no retry/backoff. The real client is still the default when `client=None` and `cache_dir` is honoured. The same seam shape the ticket-20 client uses for its own tests.
- *Lap-with-no-matching-stint → skip.* The findings call this out as an ambiguity case ("a lap missing from its stint"). A lap with no compound is useless to the predictor (it is used by Long Run detection, Historical Degradation and the Tyre Allocation tracker, all of which need a Compound), and inserting it with an "unknown compound" would turn silent data gaps into noisy false Long Runs. Matches the FastF1 loader's existing behaviour of skipping rows with missing tyre info. Pinned by `test_laps_outside_every_stint_range_are_skipped`.
- *`tyre_age` on the first lap of a new stint = 1 + tyre_age_at_start.* The findings recipe reads `(lap_number - stint.lap_start) + 1 + tyre_age_at_start`. On a fresh set that gives 1, which matches FastF1's `TyreLife` convention ("number of laps on this set, including this one"). On a used set with `tyre_age_at_start=5` (Austria sprint VER MEDIUM in the fixture, from the findings' live-sampled stint), lap 1 is age 6, lap 2 is age 7 — directly comparable with a FastF1 used-set stint reading `TyreLife = 6, 7, …`. Alternative — age = `lap_number - lap_start + tyre_age_at_start` (0-indexed) — rejected because it would silently make a fresh set's first lap read age 0, breaking any downstream code that expects "the lap you just drove on this set" to be at least 1.
- *`new_when_fitted = (stint.tyre_age_at_start == 0)`.* OpenF1 flags used-set stints with `tyre_age_at_start ≥ 1`; the findings confirm every observed `tyre_age_at_start == 0` was a new set the team was known to have fitted. Alternative — reading `/v1/stints` for an unavailable `is_new` field — is not possible, the field doesn't exist. This is the only derivation OpenF1 gives us.
- *`pit_in` from `/v1/pit.lap_number` set membership, not from a lap flag.* OpenF1 doesn't carry a `pit_in` flag on `/v1/laps` the way FastF1 attaches a `PitInTime`. The `/v1/pit` endpoint lists one row per pit stop with the lap number, which is the pit-in lap by definition (confirmed by matching the lap after against `is_pit_out_lap=True`). A per-driver `set[int]` of pit-in laps is O(1) per lap. Rejected: cross-checking against the next lap's `is_pit_out_lap=True` — redundant and masks genuine single-side data gaps.
- *`neutralised` for pre-race sessions = always False.* Recorded ambiguity: OpenF1 has no per-lap TrackStatus and the ticket is pre-race only, so reconstructing neutralisation ranges from `/v1/race_control` events for a practice session is both out of scope (ticket 22 covers race neutralisations) and of marginal value (practice red flags are rare and the loader's downstream code doesn't filter practice Long Runs by neutralised status — see `_historical_stint_rates`, which only reads race laps). The one case that visibly diverges from the FastF1 loader is a red-flag or SC-interrupted FP session; if that ever matters the fix is a `/v1/race_control`-based reconstruction akin to ticket 22's race path. Pinned by `test_neutralised_is_false_for_pre_race_sessions`.
- *Session short names: 2023 "Sprint Shootout" and 2024+ "Sprint Qualifying" both → `SQ`.* The two labels name the same session (F1 renamed it, OpenF1 follows). Mapping both to one short id lets the predictor read "SQ" from either season without a per-year lookup. The sprint race itself (`Sprint`) kept its name through the rename.
- *Pre-season testing filter on the "Grand Prix" suffix.* The findings observe that "Pre-Season Testing" is the only non-round entry in a yearly OpenF1 meetings list. A substring match on "grand prix" (case-insensitive) in `meeting_name` is one line and robust: every championship round's name ends in "Grand Prix" and nothing else does. Pinned by `test_pre_season_testing_is_not_matched_as_an_event`. Alternative — a hardcoded list of testing meeting_keys — rejected because it would need updating every season.
- *Fixtures as JSON files keyed by URL suffix, not Python dicts in a module.* JSON lets `_FixtureClient`'s key reconstruction (`endpoint?sorted_kwargs`) mirror what `OpenF1Client._build_url` would produce, which keeps the recorded shape close to a real cache file. The `_about` meta-key documents what each fixture covers. Rejected: using the client's own cache format (hashed filenames) — a hash is opaque to a human reader of the test and the ticket's "recorded responses" bar is met by either format.
- *`_FixtureClient` raises on a missing row rather than returning `[]`.* A silent `[]` would make a missing fixture look like "no data", which is a legitimate OpenF1 response (an unobserved session). Loud failure during a test is the right default; the real client never raises on a missing row.

**Deviations from the ticket / spec.**

- *The ticket's "Round number from meeting date order" derivation is implemented as `_round_number` but not called by `load_weekend`.* `PreRaceInfo` has no round field (the FastF1 loader doesn't carry it either — rounds are a `list_season` concern), so wiring it into the pre-race return value would need a dataclass change out of ticket 21's scope. The helper is tested and ready for ticket 23's `list_season` to call it directly. No spec change: `spec.md` names the derivation among the recipes the OpenF1 loader must know, not among the fields `PreRaceInfo` must carry.
- *`pit_loss` and `pit_loss_seasons` are placeholders.* The ticket's "Out of scope" paragraph explicitly says Pit Loss is ticket 22, so this is the intended split. Flagged in the loader docstring and pinned by `test_pit_loss_is_a_placeholder_in_ticket_21_scope`.
- *`race.laps` content is empty here even though `pre_race.race_laps` is populated.* `race_laps` is a pre-race field (the predictor reads it before the race begins); race Stints, neutralisations and finishing status are race-outcome fields. The split tracks the `PreRaceInfo` / `RaceOutcome` boundary rather than the "ticket 21 reads only pre-race endpoints" boundary; the one call to `/v1/session_result` here is the cheapest derivation the findings offer for `race_laps`.

**Open questions, known limitations and follow-ups.**

- *Neutralised flag on pre-race sessions is always False.* If a red-flagged FP session ever matters for Long Run or Pace detection, ticket 22's `_neutralisation_periods` recipe (events from `/v1/race_control` with lap-range reconstruction) can be reused per-session. Not needed by any current consumer.
- *Case-insensitive match on `event` may be ambiguous if a season ever contains two races at the same country.* 2023–2025 does not (Austria and Styria shared Red Bull Ring in 2020 only, pre-OpenF1 coverage). If OpenF1's historical set ever grows and such a case appears, extend `_find_meeting` to accept an exact `meeting_key` as an escape hatch.
- *`_race_laps_count` doesn't distinguish a scheduled lap count from a red-flag-shortened one.* FastF1's `race.total_laps` has the same ambiguity (whichever lap count F1 recorded), so this is a known-identical limitation across sources, not a divergence.
- *Starter list uses the main `Qualifying` session on sprint weekends.* This gives the race's starting grid, which is what the FastF1 loader's `results["GridPosition"] > 0` filter uses. The Sprint's starting grid (from `Sprint Qualifying`) is not captured — the predictor doesn't currently model sprint-specific Remaining Sets separately from the main race, and ticket 25 doesn't require it either.
- *Rate-limit budget: 17 OpenF1 requests per weekend (conventional or sprint, since both have four pre-race sessions). Breakdown: meetings 1 + sessions 1 + drivers 1 + starting_grid 1 + session_result 1 + 4 × (laps + stints + pit) = 5 + 12. A 24-race season is ~400 requests, under 14 minutes at the free-tier 30 req/min cap — well inside the budget. Warm-cache re-runs make zero requests.*
