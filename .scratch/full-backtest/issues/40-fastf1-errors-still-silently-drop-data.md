# 40: FastF1 errors can still silently drop data

**What to build:** Two FastF1 paths still turn errors into missing data, against tickets 17 and 28. (1) Loading a pre-race session catches every exception and returns nothing, so a rate-limit hit or network error on a 2022 practice session loads the weekend without that session. (2) The FastF1 past-race sampler lets only `FastF1CriticalError` through; connection errors and refused loads return empty samples, which the router then reports as "fetch succeeded with no rows", and 2022 races collect no Data Quality Warnings at all.

**Blocked by:** None (can start immediately)

**Status:** done

**Category:** bug

- [x] A rate-limit error while loading a FastF1 pre-race session reaches the Backtest's wait-and-retry; it never produces a weekend missing that session (fast test with a fake)
- [x] A network error or refused load on a FastF1 pre-race session or past race is excluded as "fetch failed" or recorded as a warning with an honest reason, never "fetch succeeded with no rows"
- [x] A session or past race that genuinely has no data (e.g. 2018–2020 behind the archive's 401, ADR-0006) is recorded with that reason
- [x] FastF1-sourced races collect Data Quality Warnings the same way OpenF1-sourced ones do
- [x] The Smoke Set is re-run and its numbers recorded

## Implementation notes

**What FastF1 actually does (checked first, 2026-10-26).** FastF1 3.8.3's `Session.load` wraps each loading step in `soft_exceptions`, which re-raises only `FastF1CriticalError` (the rate limit). Any other error is logged as a WARNING plus a DEBUG record carrying the traceback, and `load` returns with the laps missing. `get_event_schedule` works the same way, then raises a bare `ValueError("Failed to load any schedule data.")`. So from outside, a network outage, a 401 refusal and an empty session all look identical: no `_laps`. I confirmed this offline, with no archive requests, by patching `fastf1.req.Cache.requests_get` and running the real FastF1 code on an uncached 2019 Spain race:

- A simulated `requests` `ConnectionError` left no laps, with `ConnectionError` tracebacks in the DEBUG records.
- A simulated 401 left no laps, with FastF1's own `SessionNotAvailableError` in the DEBUG records.
- Both also logged unrelated `AttributeError`s from the Ergast first-lap lookup.
- A cached 2022 session loaded normally with zero requests.

**The bugs, reproduced (all fast tests, all red on the ticket-38 commit, 14 of the 15 written first).**

- Rate limit on a 2022 pre-race session: `_load_pre_race_session` had `except Exception: return None`, so the rate limit was swallowed. `load_weekend` returned a weekend without FP2, and the Backtest never waited (`DID NOT RAISE RateLimitExceededError`, wait count `0 == 1`).
- Network error on FP1, or on a pre-era past race: the weekend loaded anyway and went on to prediction. With the test's stub weekend it became `PREDICTION_FAILED`, never `FETCH_FAILED`.
- Refused 2022 past race read by a 2024 race through the router: the warning was `2022 Barcelona: no usable past-race samples (fetch succeeded with no rows or no clean laps)`.
- 2022 races collected no Data Quality Warnings at all (`[] == ['2018', '2019', '2020']`).
- Found while reading `_laps_from` (not tested on HEAD with real data): a session that *loaded* without laps would have crashed the whole weekend with FastF1's `DataNotLoadedError` ("data not loaded yet"), an Excluded Race with an unclear reason. Only sessions that *raised* were dropped silently.

**What was built.**

- `src/f1_strategy/fastf1_errors.py` (new):
  - `FastF1FetchError(RuntimeError)`.
  - `watch_fastf1()`: a context manager that adds a handler to FastF1's base logger, which is already at DEBUG, and records every logged exception by kind: network, no data, or other.
  - `missing_data_reason(what, season, problems, raised=None)`, which runs only once data is known to be missing:
    - a `requests.RequestException`, `ConnectionError` or `TimeoutError` raises `FastF1FetchError`;
    - `SessionNotAvailableError` returns "the F1 live-timing archive returned no data for it", adding "(it has refused 2018–2020 without an F1 TV login since mid-October 2026, ADR-0006)" for those seasons;
    - anything else returns a reason naming the error.
  - `ARCHIVE_REFUSED_SEASONS = (2018, 2019, 2020)`.
- `src/f1_strategy/fastf1_loader.py`:
  - New `_load_session` and `_schedule` helpers apply those rules in one place. The rate limit always propagates.
  - The target race: a network error raises `FastF1FetchError`; no laps raises a `ValueError` naming the reason (still `DATA_UNAVAILABLE`, now with an honest detail).
  - `_load_pre_race_session` returns `(session, warning)`. A session with no data is left out with a warning, e.g. `FP3: not loaded (the F1 live-timing archive returned no data for it)`.
  - `_past_races_at_circuit`, used by 2022 races for same-era and pre-era history, writes one warning per past season whose race gave no samples. The wording matches the router's (`2019 Barcelona: no usable past-race samples (FastF1 2019 round 5: …)`). A season where the circuit wasn't raced gives none.
  - `_measure_pit_loss_and_history` returns those warnings as a fifth element. `load_weekend` puts the session warnings first and the history warnings after, the same order as the OpenF1 loader, on `PreRaceInfo.data_quality_warnings`. The Backtest already copies them to the saved race (tickets 28, 39).
  - `load_past_race_samples` (the router's FastF1 branch) returns the reason in `PastRaceSamples.note`.
  - The schedule is read with `include_testing=False`; see the Smoke Set notes.
- `src/f1_strategy/openf1_loader.py`: `PastRaceSamples.note: str | None = None`.
- `src/f1_strategy/data.py`: when a past season contributed nothing, the router's warning uses the sources' notes. It falls back to "fetch succeeded with no rows or no clean laps" only when no note was given.
- `src/f1_strategy/backtest.py`: `FastF1FetchError` becomes `FETCH_FAILED` with the detail `FastF1 fetch failed: <season> <event> <session>: network error (…)`.
- Tests:
  - `tests/test_fastf1_fetch_errors.py` (new): 16 fast tests, 0.6 s. Fakes fail exactly the way FastF1 does: non-critical errors go through FastF1's real `soft_exceptions` decorator, and "refused" is FastF1's real `SessionNotAvailableError` class, which also pins the name the classifier matches on.
  - `tests/test_fastf1_loader_rate_limit.py`: the ticket-17 test that said a `ConnectionError` is "treated as no data" now pins that a `ValueError` is still no data, with a warning naming it. Its fakes gained `.empty` and accept `include_testing`.

**Decisions and alternatives rejected.**

- *Read the cause from FastF1's logged tracebacks.* It is the only place FastF1 reports it, and handlers on its logger are a documented part of FastF1's logging setup.
  - Rejected: FastF1's debug mode (`FASTF1_DEBUG=1`), which makes `soft_exceptions` re-raise everything. It would also raise for harmless side failures, such as the Ergast first-lap lookup that fails on loads that otherwise succeed, and turn good weekends into failures.
  - Rejected: wrapping `fastf1.req.Cache.requests_get` to see HTTP status codes. It patches FastF1's private request layer, the coupling ticket 17 also turned down.
- *Classify only when data is actually missing.* The Ergast case above logs `AttributeError`s, and could log network errors, on loads that succeed. A fast test pins that a logged failure on a session that loaded is ignored.
- *Match `SessionNotAvailableError` by name, not by import.* It lives in FastF1's private `fastf1._api`. If FastF1 renames it, the reason degrades to a generic "no lap data (…)" instead of the module failing to import. The fast tests use the real class, so a rename shows up there.
- *A network error excludes the race as `FETCH_FAILED`, even when it hit a past race.* This is the ticket-28 rule for OpenF1. A missing past race would quietly change Pit Loss, and the data probably exists, so a re-run on the warm cache is the right fix. Rejected: a Data Quality Warning instead, which would score the race on partial history from a transient fault.
- *No wait-and-retry for FastF1 network errors.* Ticket 17's one-hour wait is for the rate limit's sliding window, and there's no reason to think an hour fixes a network fault. FastF1 has no retry of its own (OpenF1's client retries three times).
- *A session or past race with no data is a warning, not an exclusion.* The ticket allows either. It matches what the OpenF1 loader does for dropped rows, and 2018–2020 is a known, permanent gap (ADR-0006).
- *Pre-race sessions that fail for another reason (e.g. `ValueError` from `get_session`) are a warning naming the error*, not an exclusion. It is honest, and it keeps races scored that used to be scored. The error text is in the saved result for anyone to follow up.
- *New module `fastf1_errors.py`* rather than putting the error in `fastf1_loader`. `backtest` can't import `fastf1_loader`, which already imports `backtest`, and the classifier is one rule with one job, like `rate_limit.py`.
- *Return-tuple extension for the warnings* (`_measure_pit_loss_and_history`, `_past_races_at_circuit`), not an out-parameter. Ticket 45 replaces these tuples with named types.

**Deviations from the ticket / spec.**

- *The target race itself is covered too*, though the ticket names only pre-race sessions and past races. It goes through the same helper, so a network error on it is `FETCH_FAILED` rather than FastF1's "data not loaded" crash.
- *`include_testing=False`* is a matching change, not error handling. It is one argument and removes a false error this ticket made visible.
- *The router's own pre-era pass* (`data._measure_pre_era_pit_loss`, which only a 2023+ race at a circuit with no 2022 race would reach, and none exists) still writes no warnings. Ticket 45 merges it with the FastF1 loader's pass, which does.
- No spec change: the spec doesn't describe FastF1 error handling. ADR-0006's pre-era paragraph gained a sentence on how the refusal is recorded. `CONTEXT.md`'s **Data Quality Warning** and **Excluded Race** entries were sharpened.

**Open questions, known limitations and follow-ups.**

- *Computation errors are still swallowed.* `_pit_losses_in` and `_historical_stint_rates` are wrapped in `except Exception` in both FastF1 past-race paths, so a bug in our own fitting code still reads as "no samples". The warning now says "no clean laps" for it, which may be wrong. Left alone because it is not a fetch error and ticket 45 rewrites these paths. Worth carrying into 45.
- *Ticket 43* (stop requesting 2018–2020) should keep these warnings when it skips the requests, so a 2022 race still says why its pre-era seasons are missing. `ARCHIVE_REFUSED_SEASONS` is the obvious single place to declare the range. Noted on ticket 43.
- *Saved results*: every 2022 race reaching 2018–2020 will gain one to three warnings in the next full Backtest (ticket 24's rerun), so `compare` against first-openf1-run reports them as changed warnings. That is expected, not a regression. first-openf1-run is version 1 anyway, so the compare prints "can't be compared".

**Review feedback to the user.**

- The ticket's two paths were real. The first was worse than it read: before ticket 40, a 2022 pre-race session either vanished silently (if FastF1 raised) or took the whole race down with an unclear "data not loaded" error (if it loaded without laps). Neither said "rate limit" or "network".
- The classification relies on FastF1 logging tracebacks at DEBUG through `soft_exceptions`. This is stable in FastF1 3.x but not a documented API. If a FastF1 upgrade changes it, the fast tests still pass, because they use FastF1's own decorator; but a refusal would read as "FastF1 loaded no lap data". A one-line check after any FastF1 upgrade: the Spain 2022 Smoke warnings should still name the archive.
