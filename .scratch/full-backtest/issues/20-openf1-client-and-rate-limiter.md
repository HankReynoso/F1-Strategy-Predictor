# 20: OpenF1 HTTP client and rate limiter

**What to build:** A thin HTTP client for `https://api.openf1.org/v1/` with the free-tier rate limit (3 req/s and 30 req/min), on-disk JSON cache keyed by request URL, and retry/backoff on 429/5xx. Reuses the `rate_limit.py` wait seam from ticket 17 so the limiter is testable without real sleeps.

**Blocked by:** 19 (ADR)

**Status:** done

**Category:** enhancement

Scope and the rate-limit numbers come from [`openf1-findings.md`](../openf1-findings.md) ("OpenF1 coverage, terms, limits"). Follow-up from [ticket 18](18-check-openf1-as-second-data-source.md).

**Out of scope:** anything that reads the response payloads into the weekend description — that is tickets 21 and 22.

## Implementation notes

**OpenF1 docs re-checked (2026-10-23).** Fetched `openf1.org` live before
building and confirmed the free-tier wording still reads "Up to 3 requests
per second and 30 requests per minute" and "No authentication required"
for historical sessions since 2023, licensed CC BY-NC-SA 4.0. The numbers
and terms in [`openf1-findings.md`](../openf1-findings.md) still apply
verbatim; no deviations to note.

**What was built (2026-10-23), test-first.**

- `src/f1_strategy/openf1_client.py` — one new module, ~230 lines.
  - `OpenF1Client` with one public call, `get(endpoint, **params)`,
    returning the parsed JSON list. Everything else is private: URL
    building, cache file layout, rate-limit windows, retry with backoff.
  - `HttpResponse` dataclass + `HttpGet` callable type are the HTTP seam
    — a `urllib.request` wrapper (`_default_http_get`) is the real
    implementation; tests inject a fake. Keeping the seam at this level
    (rather than passing a `requests.Session`) lets the client stay
    dependency-free and makes a fake "server" one dataclass to script.
  - `wait: RateLimitWait = default_wait` and `clock: Callable[[], float]
    = time.monotonic` are the two time seams. Tests pass a `_FakeClock`
    whose `wait()` records the pause and advances the clock in lock-
    step, so the per-second and per-minute windows evict correctly
    without any real sleep.
  - Rate limiting uses two `collections.deque` sliding windows (one for
    1 s, one for 60 s). Before each request, old timestamps are evicted
    and, if either window is full, the client waits for the oldest
    offending timestamp to leave its window. `wait()` is called at most
    once per request with the larger of the two needed delays, so a
    minute-cap wait is never followed by a redundant second-cap wait.
  - On-disk cache: SHA-256 of the full request URL as the filename
    (`<hash>.json`) under the caller-chosen cache dir. Atomic write via
    `tmp → replace`. A `.url` sidecar is written next to each payload so
    a human reader can tell cache entries apart without re-hashing. A
    cached hit short-circuits before `_fetch_with_retry`, so cached
    requests never touch `_wait_for_rate_limit` or the HTTP seam —
    which is what makes the "cached requests do not count toward the
    rate limit" acceptance criterion hold without a dedicated code path.
  - Retry/backoff: 429 and 5xx retry up to `max_retries` extra times
    (default 3). Delay honours a `Retry-After` header when present,
    otherwise `backoff_base * 2 ** attempt` with `backoff_base = 1.0`.
    Non-retryable 4xx (e.g. 404) and malformed JSON (non-list or syntax
    error) raise `OpenF1FetchError` immediately — the Backtest can map
    this to the `FETCH_FAILED` Excluded Race reason ticket 17 added.
  - A failed fetch is **not** cached. The cache file is written only
    after `_fetch_with_retry` returns a successful payload.
- `tests/test_openf1_client.py` — 20 fast tests covering fetching
  (URL-building, query encoding, non-list / invalid-JSON errors),
  caching (hit returns same payload, cache keyed by full URL, cached
  hits don't count toward the rate limit, cache survives a new client
  instance, dir created if absent), rate limiting (3 req/s allowed
  without wait, 4th waits, 30 req/min allowed without a minute-wait,
  31st waits, injected wait is used), and retries (429/5xx retried
  then succeed, persistent 429/5xx raise `OpenF1FetchError`, 404 does
  not retry, `Retry-After` steers the backoff, failed fetches aren't
  cached). The whole file runs in ~0.6 s.
- `tests/test_openf1_client_real_data.py` — one `@pytest.mark.slow`
  test that fetches `/v1/meetings?year=2024&country_name=Italy` through
  the real `urllib` seam and asserts the row for Monza comes back.
  Runs in ~1.1 s against the live endpoint, no API key.

**Cache folder is gitignored.** `.gitignore` already contains `.cache/`,
which matches any subdirectory. The convention for the loader tickets
(21–23) is to pass `cache_dir=Path(".cache/openf1")`, matching how
`fastf1_loader` uses `.cache/fastf1`. The client itself takes the
directory as an argument so tests use `tmp_path` and never touch the
project cache.

**Decisions and alternatives rejected.**

- *`urllib` over `requests` / `httpx`.* No new dependency, no `.venv`
  change, and the HTTP seam is injectable so the choice is reversible
  at the module boundary. The real `_default_http_get` is seven lines
  and all its edge cases (HTTPError → status + body) are covered by
  the fake-driven fast tests.
- *Dual sliding-window limiter over a single "max of both" cap.* Doing
  it with two deques tracks each limit on its own, so a run that
  pauses 1 s at the per-second cap doesn't carry a phantom per-minute
  wait, and the reason string names which limit fired. Alternative: a
  single combined limiter emitting the stricter wait each time. Not
  wrong, but harder to reason about and to test.
- *SHA-256 of the full URL as the cache filename.* Alternatives: a
  path-safe encoding of the endpoint + sorted query string. Rejected
  because OpenF1 URLs are long (session_key, meeting_key, driver_number
  in the same URL) and the resulting filename needs quoting on every
  OS; a 64-char hex hash is OS-safe and deterministic from the URL.
  The `.url` sidecar covers the only cost (human readability).
- *Store the response wrapped as `{"url": url, "data": [...]}`.*
  Rejected because the data is already a list and keeping the on-disk
  layout flat means a reader can `cat <hash>.json | jq .` without
  knowing the wrapper. The `.url` sidecar covers the URL-identification
  need separately.
- *Cache failed fetches too (negative caching).* Rejected: a 5xx is
  transient almost by definition, and caching it would make a warm-
  cache re-run never recover. The acceptance criterion only requires
  cache hits to not re-fetch; it does not demand negative caching.
- *Honour `Retry-After` only on 429.* Honoured on 5xx too, which is
  harmless (most 5xx responses don't carry one) and avoids a surprise
  if OpenF1 later uses it for 503. Non-numeric `Retry-After` (HTTP-date
  form) is ignored and the exponential back-off is used instead; this
  is covered by the parse-fallback branch of `_parse_retry_after`.
- *`default_wait` from `rate_limit.py` as the default.* Ticket 17 built
  this as the one place "we are waiting on an external limit" is
  printed to stderr. Reusing it keeps the user-visible behaviour of a
  cold Backtest consistent across the two sources: a visible "waiting
  X s because of …" line. For OpenF1 the typical wait is sub-second
  (3 req/s cap), so these messages will be noisier than FastF1's
  hourly one; this is acceptable noise on a cold cache and silent on
  a warm one.
- *Pin the rate-limit numbers (3 / 30) as module-level constants.* Pins
  the acceptance criterion in code and makes it one grep to find if
  OpenF1 changes its policy. The constants are also importable by the
  fast tests, so `MAX_REQUESTS_PER_SECOND` not being 3 would break the
  tests, not just the behaviour.

**Deviations from the ticket / spec.** None. `spec.md` is unchanged;
`CONTEXT.md` is unchanged (OpenF1 is a data source, not a strategy
term); no new ADR is needed because [ADR-0006](../../docs/adr/0006-per-season-data-source.md)
already records the per-season policy this client implements.

**Open questions, known limitations and follow-ups.**

- *The default wait is `rate_limit.default_wait` which prints to stderr
  and really sleeps.* Fine for the fetch-heavy loader tickets (21–23).
  If a future interactive use ever wants silence, a quieter
  implementation can be passed through the `wait` parameter without
  touching `openf1_client`.
- *No concurrent-fetch support.* The sliding windows are not thread-
  safe, and the cache's atomic rename works between processes but
  nothing arbitrates concurrent writes to the same URL. The project
  runs one Backtest at a time today — out of scope here.
- *`get()` returns `list[dict]`.* Every OpenF1 endpoint used so far
  responds with a JSON list; a response of a different shape is
  treated as a fetch error. If a future endpoint responds with an
  object (none observed in the ticket 18 probes), the client needs
  loosening.
- *HTTP-date `Retry-After` values are ignored.* The parse falls back
  to exponential back-off; a server that only emits HTTP-date-form
  `Retry-After` headers would wait longer than strictly necessary.
  OpenF1's observed behaviour so far is to not emit `Retry-After` at
  all, so this is a theoretical loosening.

**Review feedback for the user.** None. The client is self-contained
and the loader tickets (21–23) will wire it into `load_weekend`.
