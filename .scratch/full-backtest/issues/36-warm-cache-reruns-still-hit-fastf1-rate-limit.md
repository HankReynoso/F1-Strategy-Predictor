# 36: Offline mode: run a Backtest from saved data only

**What to build:** An `--offline` option for the `backtest` and `smoke` commands (and the single-race command, if cheap) that runs entirely from data already downloaded, never contacting FastF1 or OpenF1. A full Backtest on a warm cache then takes minutes, with no rate-limit waits. Online mode stays the default for fetching new data.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**Category:** bug

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Add a cache-only offline mode so re-runs never wait on FastF1's hourly limit.

**Current behavior:**
- OpenF1 is already effectively offline on a warm cache: its responses are cached by URL and never expire (ticket 42 measured zero requests on a warm Smoke Set run).
- FastF1 is not. Its HTTP cache treats some saved responses (notably Ergast/Jolpica results, laps and qualifying) as expired and re-requests them, and every re-request counts toward the 500-calls-per-hour limit. Full warm-cache re-runs therefore wait an hour at a time (evidence below; ticket 50's comparison run was cancelled for this reason).
- FastF1 has a built-in offline mode, but ticket 42 found the FastF1 loader calls `fastf1.Cache.enable_cache` on every load, which builds a new HTTP session and silently switches offline mode off again.
- In offline mode FastF1 reports a refused (uncached) request the same way as an archive refusal (ticket 42), so a missing race could be mistaken for an unavailable season.

**Desired behavior:**
- With `--offline`, a run makes **no** network requests to FastF1 or OpenF1 for its whole duration, including past races read for history.
- Anything not in the saved data is reported honestly: a race that can't be built from the cache is an Excluded Race with a distinct "not downloaded" reason; a past race missing from the cache is a Data Quality Warning saying it wasn't downloaded (not "archive refused", not "no clean laps").
- With the same cache, an offline run's results are identical to an online run's (except where online would have fetched something new).
- The saved Backtest Result records whether the run was offline.
- FastF1's cache is enabled once per run, not once per load, in both modes.

**Key interfaces:**
- The command: `--offline` on `backtest` and `smoke`.
- The FastF1 loader and the router: one cache setup per run; offline mode survives every load.
- The OpenF1 client: a cache-only mode that raises a clear "not downloaded" error instead of fetching.
- `ExclusionReason` and Data Quality Warnings: a "not downloaded" reason, distinct from fetch failed and archive refused.
- Run metadata in the saved result: an offline flag (follow ADR-0005's versioning rule).

**Acceptance criteria:**
- [ ] `backtest --offline` and `smoke --offline` make no FastF1 or OpenF1 network requests (a fast test with fakes that fail on any request, plus a real warm-cache Smoke Set run showing none)
- [ ] Offline mode stays on across every race and past race in a run; FastF1's cache is set up once per run
- [ ] A race missing from the cache is excluded as "not downloaded"; a missing past race gives a "not downloaded" warning; neither is reported as archive refused or no clean laps
- [ ] On the warm laptop cache, `smoke --offline` gives byte-identical results to an online Smoke Set run
- [ ] A full `backtest 2022 2023 2024 2025 --offline` on the warm laptop cache completes with no rate-limit waits; its time is recorded, and its scores match the 2026-10-27 baseline for the same code (or every difference is explained)
- [ ] The saved Backtest Result records the offline flag
- [ ] The README explains when to use offline vs online mode and corrects the warm-cache run-time notes

**Out of scope:**
- A processed data snapshot (saving built race weekends rather than raw API responses); a possible later improvement for speed and cloud sessions
- Skipping 2018–2020 requests in online mode (ticket 43)
- Other efficiency work (ticket 44)

## Comments

**Original report (2026-10-26).**

**Found 2026-10-26** during the baseline re-run after tickets 29–31 and 30, on the laptop with a warm cache. For 2022 races the log shows repeated tracebacks like:

```
Request for URL https://api.jolpi.ca/ergast/f1/2022/16/results.json failed; using cached response
...
fastf1.exceptions.RateLimitExceededError: any API: 500 calls/h
```

followed eventually by `FastF1 rate limit hit while loading 2022 Italian Grand Prix …; waiting 60 min`. What's happening:

- FastF1's request cache (requests-cache) considers some cached responses stale, notably Ergast/Jolpica results, laps and qualifying, and tries to re-download them. Each attempt counts toward FastF1's 500-calls-per-hour limit.
- When the limiter blocks a re-download, requests-cache logs the traceback and serves the saved copy, so the data is unchanged. When a request has no usable saved copy, the limit propagates and ticket 17's wait kicks in.
- So results are correct, but re-runs are slow and the log is flooded. The README's statement that warm-cache runs never wait is wrong for FastF1-sourced data.

This matters before tuning, which will need many full re-runs.

Possible directions (to decide at triage): FastF1's offline mode (use only the cache, never revalidate) for re-runs, either automatically when the cache is warm or via a flag; or configuring FastF1's cache so past-season responses never expire, since finished races don't change. Either way, a missing cache entry in offline mode must surface as a clear Excluded Race reason, never as silently missing data (ticket 28's rule).

- [ ] The results of that run are identical to a normal run on the same cache
- [ ] A race whose data isn't in the cache still loads normally on a normal run, and in any cache-only mode is excluded with a clear "not in cache" reason
- [ ] The requests-cache tracebacks no longer flood the output on a warm run
- [ ] The README's run-time notes are corrected
