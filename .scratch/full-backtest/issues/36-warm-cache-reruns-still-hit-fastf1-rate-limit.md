# 36: Offline mode: run a Backtest from saved data only

**What to build:** An `--offline` option for the `backtest` and `smoke` commands (and the single-race command, if cheap) that runs entirely from data already downloaded, never contacting FastF1 or OpenF1. A full Backtest on a warm cache then takes minutes, with no rate-limit waits. Online mode stays the default for fetching new data.

**Blocked by:** None (can start immediately)

**Status:** done

**Category:** bug

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Add a cache-only offline mode so re-runs never wait on FastF1's hourly limit.

**Current behavior:**
- OpenF1 is already effectively offline on a warm cache: its responses are cached by URL and never expire (ticket 42 measured zero requests on a warm Smoke Set run).
- FastF1 is not. Its HTTP cache treats some saved responses (notably Ergast/Jolpica results, laps and qualifying) as expired and re-requests them, and every re-request counts toward the 500-calls-per-hour limit. Full warm-cache re-runs therefore wait an hour at a time (evidence below; ticket 50's comparison run was cancelled for this reason).
- FastF1 has a built-in offline mode, but ticket 42 found the FastF1 loader calls `fastf1.Cache.enable_cache` on every load, which builds a new HTTP session and silently switches offline mode off again.
- In offline mode FastF1 reports a refused (uncached) request the same way as an archive refusal (ticket 42), so a missing race could be mistaken for an unavailable season.

**Desired behavior:**
- With `--offline`, a run makes **no** network requests to FastF1 or OpenF1 for its whole duration, including past races read for history.
- Anything not in the saved data is reported honestly: a race that can't be built from the cache is an Excluded Race with a distinct "not downloaded" reason; a past race missing from the cache is a Data Quality Warning saying it wasn't downloaded (not "archive refused", not "no clean laps").
- With the same cache, an offline run's results are identical to an online run's (except where online would have fetched something new).
- The saved Backtest Result records whether the run was offline.
- FastF1's cache is enabled once per run, not once per load, in both modes.

**Key interfaces:**
- The command: `--offline` on `backtest` and `smoke`.
- The FastF1 loader and the router: one cache setup per run; offline mode survives every load.
- The OpenF1 client: a cache-only mode that raises a clear "not downloaded" error instead of fetching.
- `ExclusionReason` and Data Quality Warnings: a "not downloaded" reason, distinct from fetch failed and archive refused.
- Run metadata in the saved result: an offline flag (follow ADR-0005's versioning rule).

**Acceptance criteria:**
- [x] `backtest --offline` and `smoke --offline` make no FastF1 or OpenF1 network requests (a fast test with fakes that fail on any request, plus a real warm-cache Smoke Set run showing none)
- [x] Offline mode stays on across every race and past race in a run; FastF1's cache is set up once per run
- [x] A race missing from the cache is excluded as "not downloaded"; a missing past race gives a "not downloaded" warning; neither is reported as archive refused or no clean laps
- [x] On the warm laptop cache, `smoke --offline` gives byte-identical results to an online Smoke Set run
- [x] A full `backtest 2022 2023 2024 2025 --offline` on the warm laptop cache completes with no rate-limit waits; its time is recorded, and its scores match the 2026-10-27 baseline for the same code (or every difference is explained)
- [x] The saved Backtest Result records the offline flag
- [x] The README explains when to use offline vs online mode and corrects the warm-cache run-time notes

**Out of scope:**
- A processed data snapshot (saving built race weekends rather than raw API responses); a possible later improvement for speed and cloud sessions
- Skipping 2018–2020 requests in online mode (ticket 43)
- Other efficiency work (ticket 44)

## Comments

**Original report (2026-10-26).**

**Found 2026-10-26** during the baseline re-run after tickets 29–31 and 30, on the laptop with a warm cache. For 2022 races the log shows repeated tracebacks like:

```
Request for URL https://api.jolpi.ca/ergast/f1/2022/16/results.json failed; using cached response
...
fastf1.exceptions.RateLimitExceededError: any API: 500 calls/h
```

followed eventually by `FastF1 rate limit hit while loading 2022 Italian Grand Prix …; waiting 60 min`. What's happening:

- FastF1's request cache (requests-cache) considers some cached responses stale, notably Ergast/Jolpica results, laps and qualifying, and tries to re-download them. Each attempt counts toward FastF1's 500-calls-per-hour limit.
- When the limiter blocks a re-download, requests-cache logs the traceback and serves the saved copy, so the data is unchanged. When a request has no usable saved copy, the limit propagates and ticket 17's wait kicks in.
- So results are correct, but re-runs are slow and the log is flooded. The README's statement that warm-cache runs never wait is wrong for FastF1-sourced data.

This matters before tuning, which will need many full re-runs.

Possible directions (to decide at triage): FastF1's offline mode (use only the cache, never revalidate) for re-runs, either automatically when the cache is warm or via a flag; or configuring FastF1's cache so past-season responses never expire, since finished races don't change. Either way, a missing cache entry in offline mode must surface as a clear Excluded Race reason, never as silently missing data (ticket 28's rule).

## Implementation notes

**Status: done.** All seven acceptance criteria of the Agent Brief pass (evidence below). The checklist under "Original report" is the pre-triage wording, superseded by the Brief, and is left as it was.

**What FastF1 does offline (checked first, 2026-10-27, FastF1 3.8.3, requests-cache 1.3.3).**

- `Cache.offline_mode(True)` sets `only_if_cached` on FastF1's cached HTTP session. With FastF1's `stale_if_error=True`, requests-cache then serves every saved response, stale ones included, and answers a miss with a synthetic 504 without sending anything. So offline mode fixes the warm-cache revalidations at the source.
- Every FastF1 request goes through `Cache.requests_get`/`requests_post` and that session. The only other network call in the package is F1 TV login (`internals/f1auth.py`), which the project never uses.
- `enable_cache` builds a new session, which starts online. That is ticket 42's finding: calling it on every load turned offline mode off.
- An offline miss, probed on an empty cache with sockets blocked: no network errors, FastF1's `SessionNotAvailableError` plus unrelated `JSONDecodeError`/`TypeError`s, and the schedule raises `ValueError("Failed to load any schedule data.")`. Zero socket connections. As ticket 42 said, it looks like a refusal.
- requests-cache only stores 200 responses, so a refusal or a missing session is never saved. Offline, "no data" therefore always means "not in the saved data".

**What was built, test-first.**

- `src/f1_strategy/offline.py` (new): `NotDownloadedError` and `NOT_DOWNLOADED_REASON`, shared by both sources and the Backtest.
- `fastf1_loader.py`:
  - `set_up_cache(cache_dir, *, offline)` enables FastF1's cache once and, when offline, turns offline mode on. `is_offline()` reports it.
  - `_ensure_cache(cache_dir)` replaces the four `enable_cache` calls in `load_weekend`, `list_season`, `_past_races_at_circuit` and `load_past_race_samples`. It does nothing when the run's cache is already set up for that directory, and re-enables with the run's mode otherwise. A direct caller that never called `set_up_cache` (notebook, older tests) gets an online cache, as before.
  - Offline, a target race with no data raises `NotDownloadedError` (online it is still `ValueError`, `DATA_UNAVAILABLE`). A season listing that misses raises `NotDownloadedError` too.
- `fastf1_errors.missing_data_reason(..., offline=False)`: offline, missing data is `NOT_DOWNLOADED_REASON`, except for `ARCHIVE_REFUSED_SEASONS` (2018–2020), which keep the archive reason (see decisions). Pre-race sessions and past races get this through `_load_session` and `_schedule`.
- `OpenF1Client(..., offline=False)`: a cache miss raises `NotDownloadedError` instead of fetching. Cached responses, including the cached empty lists for OpenF1's "No results" 404s, are served as before.
- `data._fetch_past_samples`: an OpenF1 past race that raises `NotDownloadedError` becomes empty samples with the error as the note, so the router's existing Data Quality Warning names it.
- `backtest.py`: `ExclusionReason.NOT_DOWNLOADED = "not downloaded (offline run)"`, caught before the fetch-failed cases. The `run_backtest` docstring no longer claims warm-cache runs never wait.
- `backtest_io.py`: `RunMetadata.offline: bool = False`, saved as `metadata.offline`; the summary gains a `- Data: online` / `offline (saved data only)` line.
- `cli.py`: `--offline` on `backtest`, `smoke` and the single-race command. `_fastf1_load_and_list(offline)` calls `set_up_cache` once per command and builds the run's one OpenF1 client with the same mode. The stderr header says when a run is offline.
- `tests/test_offline_mode.py` (new), 17 fast tests, 0.8 s. They run the real FastF1 library and the real OpenF1 client on empty or seeded caches in `tmp_path`. A fixture replaces `socket.socket.connect`/`connect_ex` with one that records the attempt and fails, so any network request fails the test; OpenF1 fakes raise on any HTTP call. A second fixture restores FastF1's process-wide cache state so no later test is left offline.

Red first: the whole new file failed at collection (`ModuleNotFoundError: f1_strategy.offline`) before any code was written. I didn't run each test separately against the old code.

**Decisions and alternatives rejected.**

- *FastF1's own offline mode, kept alive by one cache setup per run.* It is FastF1's documented switch, and it stops the stale-response revalidation at its source.
  - Rejected: making past-season responses never expire (the original report's other direction). It would also have helped online runs, but it means reaching into requests-cache's settings on FastF1's private session, and an online run would still send a request for every miss. The Brief chose an explicit switch.
  - Rejected: turning offline on automatically when the cache looks warm. Nothing cheap tells a warm cache from a partly warm one, and a silent switch would make "not downloaded" exclusions appear for no reason the user chose.
- *`_ensure_cache` keyed on the resolved cache directory, with the run's state held in `fastf1_loader`.* FastF1's cache is process-wide, so the loader's record of it is too. The loaders keep their `cache_dir` parameters and still work for direct callers.
  - Rejected: removing `enable_cache` from the loaders entirely and relying on the CLI. Every direct caller (the notebook, slow tests, scripts) would then silently use FastF1's default cache in the user's home directory.
  - Rejected: reading FastF1's private `Cache._CACHE_DIR` to see what is enabled. Same private-coupling reason tickets 17 and 40 gave.
  - A load under another directory keeps the run's offline mode, so a run can never quietly go back online.
- *Offline, every missing piece is "not downloaded", except 2018–2020.* requests-cache only saves 200 responses, so offline nothing distinguishes "never asked" from "asked and refused"; "not downloaded" is the honest reading. 2018–2020 are refused for a known, standing reason (ADR-0006), and an online run reports exactly that. Giving them the same reason offline keeps criterion 4 (byte-identical Smoke Set) true and stops Spain 2022's warnings changing wording between modes. The Brief's concern, a race the archive *does* serve being mistaken for a refused one, can't happen: any other season says "not downloaded".
  - Rejected: "not downloaded" for 2018–2020 too. Spain 2022's three warnings would change between modes, failing criterion 4, for seasons that can't be downloaded anyway.
  - Rejected: detecting requests-cache's synthetic 504s. FastF1 doesn't log the status, and reading it means patching FastF1's private request layer (tickets 17, 40).
- *A missing OpenF1 past race is a warning; a missing target race or pre-race OpenF1 request excludes the race.* That is what the Brief asks. It differs from tickets 28 and 40, which exclude a race whose past race had a network error. There, the data probably exists and a retry fixes it; here, the user chose to run offline, and the warning says exactly what to fetch.
- *FastF1 pre-race sessions missing offline are a warning* (`FP3: not loaded (not downloaded …)`), as a missing session already is online. An OpenF1 weekend, which fetches its sessions as part of the race, is excluded instead. Each follows its loader's existing rule.
- *One shared `NotDownloadedError`, not a subclass of either source's fetch error.* Subclassing `OpenF1FetchError` would route it to `FETCH_FAILED` wherever the order of `except` clauses slipped.
- *No format-version bump for `offline`.* ADR-0005 bumps when a missing field would read as a real value rather than "not recorded". Here the default, `false`, *is* the real value for every older file, since offline mode didn't exist. ADR-0005 now records this.
- *`--offline` on the single-race command too.* It was one argument.

**Seasons judged on (CLAUDE.md).** No modelling option, setting or rule was chosen by comparing scores. The full-Backtest comparison checks identity, not quality; it is reported with the Tuning Seasons and the Held-out Season apart.

**Open questions, known limitations and follow-ups.**

- *Online warm-cache runs still revalidate and can still wait an hour.* Offline mode avoids this; it doesn't fix online. The original report's "tracebacks no longer flood the output" therefore holds offline only. New ticket 60 (`needs-triage`) covers the online side.
- *The single-race command, offline, with a race not downloaded raises `NotDownloadedError` with a traceback*, as it raises `ValueError` online for a race with no data. That is consistent with today's single-race behaviour; a clean message for both would be a small change.
- *The slow real-data tests weren't run.* They go online. The Smoke Set and full Backtest above went through the same code with real data. `test_smoke_set_real_data.py`'s Singapore pins (4.0 / 8.0 / 2) are stale because of ticket 50, not this ticket; ticket 50 already notes the update (5.0 / 10.5 / 2, now measured here).
- *An offline run's results depend on the cache it reads.* The saved metadata says "offline" but not which cache. Comparing two machines' offline results compares two caches.
