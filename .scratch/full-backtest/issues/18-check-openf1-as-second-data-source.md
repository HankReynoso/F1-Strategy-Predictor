# 18: Check OpenF1 as a second data source

**What to build:** A findings document, not code: does OpenF1 provide everything the race weekend description needs for 2023–2025, so a second loader could replace FastF1 for the seasons FastF1 can no longer download? End with a recommendation the user can decide on.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**Category:** enhancement

## Why

Since mid-October 2026, F1's live-timing archive (`livetiming.formula1.com/static`) returns HTTP 401 to unauthenticated clients, and FastF1's mirror only serves 2021 and 2022 ([FastF1 issue #978](https://github.com/theOehrly/Fast-F1/issues/978)). On a cold cache, every 2023–2025 race and every 2018–2020 history race fails with `DataNotLoadedError`. The second baseline attempt (2026-10-23) scored 15 of 92 races for this reason; see ticket 09's Comments. The loader is the only module that knows about FastF1, so a second source is feasible if the data is there.

## Agent Brief

> *This was generated by AI during triage.*

**Current behavior:** The FastF1 weekend loader is the only data source. It can still load 2021–2022 (via FastF1's mirror) but not 2018–2020 or 2023 onward.

**Desired behavior:** A written, evidence-based answer to: can OpenF1 supply, for every 2023–2025 race weekend, each field the race weekend description uses today? For each field, record the OpenF1 endpoint and field that provides it, or that it's missing, checked against real API responses for at least one conventional weekend, one sprint weekend and one Neutralised Race. Fields to check, matching what the FastF1 loader builds today:
- event schedule: location, round, sprint or conventional format, all sessions (FP1–FP3, sprint, qualifying, race)
- per driver per lap in every session: lap time, lap number, Compound, tyre age, Tyre Set identity or new/used when fitted, pit in and pit out flags
- pit lane timing good enough for Pit Loss (pit in/out times or pit duration)
- race Stints, Safety Car and VSC periods per lap, each starter's team, and finishing status (took the chequered flag or not)
Also record: which seasons OpenF1 covers, rate limits and access rules (free use, keys, terms), response times, and any data quality issues seen (missing laps, odd Compound labels).

**Key questions to answer:**
- Is every field available, or which are missing, and could the model work without them (e.g. Tyre Set identity for Remaining Sets, ADR-0002)?
- Does using OpenF1 for 2023+ and FastF1 for 2022 (and history) still give one consistent race weekend description?
- What would the second loader cost to build, roughly in tickets?

**Acceptance criteria:**
- [ ] A findings document in the repo, with a field-by-field table (field, FastF1 source today, OpenF1 endpoint/field or "missing", notes), backed by real responses for the three weekend types above
- [ ] OpenF1's season coverage, rate limits and terms of use are recorded with links
- [ ] A clear recommendation: build a second loader (with a rough ticket breakdown), or don't (and why), plus any ADR it would need
- [ ] FastF1 issue #978's status at the time of writing is recorded
- [ ] No production code changes

**Out of scope:**
- Building the OpenF1 loader
- Any model, scoring or Backtest change
- Paid or authenticated data sources (e.g. F1 TV tokens)
